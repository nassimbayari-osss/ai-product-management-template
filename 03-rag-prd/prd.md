## Problem & user

RocketShip PMs need evidence-based prioritisation. Juno reads the strategy and the customer signal, ranks the backlog, and defends every call with a citation, inside limits a human set on purpose.

## 01 Context · Data Requirements

**Required sources, and exclusions**

Required sources

RocketShip Strategy One-Pager — the strategy document loaded by the PM for the current request. This is the source of truth for strategic priorities, decision rules, and explicit “not doing” guidance.
RocketShip product and support tickets — current ticket records available through read_tickets(), including ticket descriptions and occurrence counts.
Current user/customer evidence — interview transcripts or product signals supplied as part of the current task.

Excluded from V1

Slack messages and channels
Email
Customer-facing communications
Unapproved external documents or public web content
Historical model-generated recommendations as strategic evidence
Any source Juno cannot retrieve through an approved tool

Juno should prioritize current, approved RocketShip evidence over generic model knowledge. The model must not treat its pretrained knowledge as evidence of RocketShip strategy or customer priorities.

**SLA of truth**

The loaded strategy document is the source of truth for the current request.
Any change to the loaded strategy document must be reflected in the next request.
Strategic clauses should not be cached across requests.
Ticket data should reflect the latest available ticket state at retrieval time.
If a required source is unreachable, Juno must not silently substitute stale or invented information.
Affected recommendations should be marked Unverified, with a human-readable explanation of the missing source.

## 02 Tools · System Capabilities

**The verb list**

The verb list
search_strategy(query) — READ
Retrieves relevant clauses from the loaded strategy document.
Returns the clause text and heading.
read_tickets(filter) — READ
Retrieves current product/support ticket evidence matching a filter.
draft_priority(insight_id, priority, rationale) — DRAFT
Creates or updates a proposed priority for PM review.
Does not change committed roadmap state.
write_roadmap(insight_id, priority) — WRITE
Commits an approved priority to roadmap state.
Requires explicit human confirmation before execution.

**Deliberate omissions**

Juno does not have Slack, email, customer messaging, delete/archive, or other destructive/send capabilities in V1.
These capabilities are intentionally excluded because Juno's V1 job is evidence-backed prioritization, not autonomous communication or broad system administration.
Adding send or destructive tools would increase the blast radius without improving the core prioritization workflow.

## 03 Loop · AI Costs & Latency

**Turn ceiling and escalation**

Juno may run for a maximum of 5 agent turns per request.
If the fifth turn is reached, Juno returns the best current answer labeled “Turn limit reached.”
Juno must not silently truncate the response or pretend the workflow completed normally.
If the same tool fails 3 consecutive times, Juno stops retrying and escalates with a human-readable explanation.
A WRITE action pauses the loop for human confirmation before execution.

**Latency and cost target**

Target p95 latency under 8 seconds per request.
Track cumulative model/tool token cost for every request.
Display cumulative token cost in the tool trace.
Log requests that exceed the 8-second latency target.
Minimize unnecessary turns because each additional turn increases both latency and model cost.

## 04 Memory · Data Requirements

**What persists, at what scope**

V1 uses request-scoped memory only.

Within the current request, Juno may retain:

Retrieved strategy clauses
Retrieved ticket evidence
Tool results
Draft priorities
Human approval or rejection decisions
Verification results
This context expires when the request ends.
No user-specific preferences, prior model recommendations, or human decisions automatically carry into another PM's request.
The loaded strategy document is available to the current workflow but is not treated as permanent model memory.
Juno does not use previous model recommendations as strategic evidence.

**Expiry and write rules**

Request context expires at the end of the request.
Draft priorities persist only within the current draft/workflow until committed or discarded.
An approved roadmap decision becomes authoritative roadmap state outside Juno's model memory.
Human corrections always outrank model-generated recommendations.
Juno must not create persistent memory from its own recommendations in V1.
There is no automatic learning from prior model outputs.

## 05 Permissions · AI Risks & Mitigations

**The autonomy dial**

| Side-effect class | Tier |
|---|---|
| read | auto |
| draft | auto |
| write | confirm |
| send | blocked |

**Justification**

READ → AUTO

Reading strategy and ticket evidence is low-risk and reversible.
Requiring human confirmation for every retrieval would add friction without meaningful protection.

DRAFT → AUTO

Drafting a recommendation has limited blast radius because it does not change committed roadmap state.
The PM can inspect, reject, or revise the recommendation before anything is committed.

WRITE → CONFIRM

Writing a priority changes shared roadmap state and can influence engineering and business decisions.
Juno can propose the write, but it cannot execute it without explicit human approval.
The confirmation must show:
The insight
Proposed priority
Rationale
Supporting strategy clause
Approve / Reject controls
If the PM rejects the write, the rejection is returned to the loop as an observation so Juno can revise its recommendation.
The human decision and timestamp are logged.

SEND → BLOCKED

Outbound communication could create external commitments or represent RocketShip's position without human review.
Send capabilities are outside the V1 product job, so they are unavailable rather than merely requiring confirmation.

## 06 Verification · AI Testing & Measurement

**The check before output ships**

Before an insight is presented as a strategically grounded recommendation, Juno verifies that:

The priority is supported by a clause actually returned by search_strategy() during the current request.
The supporting clause exists verbatim in the currently loaded strategy document.
The source heading and clause are available for the PM to inspect.
The recommendation follows the applicable strategic decision rules.
Anti-patterns are identified, including:
Competitor-driven requests
Vanity or optics requests
Vague requirements
Arbitrary deadlines
Executive opinions without user evidence

An insight is marked Verified only when its supporting source evidence passes these checks.

If more than half of generated priorities are unverified, Juno displays a Low grounding warning.
Unverified insights are shown honestly rather than silently removed.

**Failure behaviour**

If verification fails:

Show the insight with an Unverified badge.
Explain that no supporting clause was found in the loaded strategy document.
Do not present the recommendation as strategically grounded.
Allow the PM to review the underlying evidence.
Prevent the insight from being written to the roadmap.

If no strategy document is loaded:

Insights may still be surfaced as product observations.
Every strategic recommendation is marked Unverified.
Juno explains that the priorities reflect the available request/evidence rather than confirmed strategic alignment.
Unverified priorities cannot be committed to the roadmap.

If a required tool or source fails:

Return the best available result with a clear explanation of what could not be verified.
Do not invent evidence or silently substitute missing information.

## Out of scope

Any capability not in the verb list above, and any action tiered `blocked`. Both are decisions on the record, not omissions.

## Harness architecture (Juno PM)

**Archetype: Supervised agent**

The task repeats at volume and success is machine-checkable, which is the only combination that justifies the engineering. It is unshippable until the Module 6 evals exist.

| Surface | Setting |
|---|---|
| 01 Context | Let the model fetch on demand through a read tool, with a per-turn assembly cap so the window does not flood. |
| 02 Tools | Only the verbs this task needs. Omissions documented. |
| 03 Loop | Ceiling of 3 to 5 turns. Escalate after 2 consecutive failed tool calls. Target p95 under 8 seconds. |
| 04 Memory | Durable, with a TTL per fact. Human corrections outrank stored model output and never expire silently. |
| 05 Permissions | read auto, draft auto, write confirm, send blocked in V1 |
| 06 Verification | Automated check runs before the output reaches a human. Define the pass bar in Module 6. On failure: Block the output and retry once, then escalate. |

### Drivers

- **Blast radius**: The whole company
- **Recoverability**: Yes, with effort
- **Verifiability**: A machine can check it
- **Repetition**: Many times a day
- **Latency budget**: 2 to 8s
